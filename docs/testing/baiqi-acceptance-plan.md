# 白绮【为我前驱】测试与验收方案

版本：2026-10-31。关联[需求 BR-001～BR-028](../requirements/baiqi-requirements.md)与[用例 TC-001～TC-040](baiqi-test-cases.md)。

**状态：方案已编写，实测未开始。** 本页中的地图、存档、故障注入与诊断字段都是待准备的测试条件；目前没有测试夹具已生成、游戏功能已通过或性能达标的结论。本机已安装游戏、找到原版调用点和本地模型 HTTP 成功，分别属于环境、源码预研与文档辅助证据。

## 验收组织

先验证单人本地白绮，建议从《风云变幻》规则集开始；精确 DLC、所属文明和版本在首次实测前固定。原版生产界面是首个兼容基线，其他模组每个组合单列。多人、热座和 AI 自动使用本领袖不属于已承诺的支持范围；若以后声称支持，必须补对应测试。

每项测试依次区分三层证据：

1. **静态与逻辑验证**：数据库／文本引用、动作白名单、规划器与结算逻辑；模拟状态可以验证分支，但不能证明引擎接受请求。
2. **引擎行为验证**：在受控单人地图中发出实际请求，读回所有权、队列、行动、资产与费用；先做普通建筑、区域、建造者和移民，再测试归属转移。
3. **完整游玩验证**：五城二十回合、十城性能、手动接管与读档，观察模块共同运行。前两层只通过部分功能时，不能跳到全功能可玩结论。

实现若采用 Lua、SQL 或其他方式，应选择该方式真正需要的检查。没有编译过程就记录“编译不适用”，不能将其写成编译通过。此方案不预设不存在证据的城市转移 API、原子交易或游戏调试接口。

## 验收配置

每次运行建立一个不可在中途改动的 `profile_id`，对每个参数记录值、单位和来源。参数变更生成新版本，并重跑受影响用例。未定项写 `TBD`，不留隐含默认值；引用该项的测试记 `BLOCKED`，不记通过。

| 字段组 | 必填内容 |
| --- | --- |
| 构建与机器 | 模组 Git SHA／工作区状态、游戏 Build 与可执行文件 SHA-256、机器 ID、CPU／内存／显卡、日期和时区。本机预研基线为 Steam Build `15296837`、机器 `BF-202609141645`，正式跑测时重新读取。 |
| 游戏规则 | 资料片／规则集、全部启用模组及版本、语言、文明与领袖、难度、速度、地图类型、种子与大小、回合模式。保存起始存档 SHA-256，记录测试前必要的手动准备。 |
| 托管策略 | 默认开关、明确文职类型／动作白名单、规划时机、每次规划的候选／请求／重试上限、手动接管规则、保护地块及财政／资源／人口／招募／扩张预算。 |
| 夺取资格 | 玩家状态、单位类型、距离 `R`、外交状态、城防条件、生命阈值 `H`、特殊城市／资产类别的资格；未启用的条件明确记“该规则未采用”。 |
| 夺取报价 | 币种与费用函数 `C(target,state)`、取整方式、行动消耗 `A`、冷却 `K`、每回合次数、报价变化处理。任一费用变更不得悄悄沿用旧确认。 |
| 转移与资产 | 转移成功的独立状态判据、资产保留／转换／损坏规则、人口／占领／忠诚度／驻军处理、建筑／区域／改良的所有者或使用控制及收益来源。 |
| 性能 | 十城样本长度与预热长度、规划时间预算 `B_plan`、单回合累计预算 `B_turn`、请求上限 `N_req`、可接受额外回合耗时 `B_delta`，以及对应测量方法。数值须在测量前确定，不能事后按结果放宽。 |
| 恢复与兼容 | 存档格式版本、支持的模组升级路径、冲突写入者处理、故障注入点与恢复步骤。注入点只有实现后才可声明可用。 |

金币草案下，余额边界分别为 `C-1`、`C`、`C+1`，每次从独立起始存档重测，所有其他资格一致；若最终改为其他离散资源，采用该资源的最小计量单位。零费用与不适用边界另行说明。`H±1`、`R±1`、冷却 `K` 等仅在规则采用这些参数时执行；不能将未采用的草案条件当成失败。

## 取证与防止误判

每个用例至少保存前态、玩家动作／模组请求、引擎后态和判定理由。截图用于确认界面、位置和实际归属；生产进度、金钱、次数与资产列表应再从游戏可核实状态读回。模组自己的“success”日志或请求已发出不能单独作通过证据。

建议诊断记录包含运行／请求关联号、回合、动作来源、当前与目标所有者、城市／单位／地块标识、报价与结算、结果状态及跳过原因。**这些是待实现的证据字段，不是已存在的 Civ6 API。** 不要求转移后城市 ID 永远相同；若引擎重编号，用位置、城市与资产映射证明真实同一座城市，而不是销毁重建。记录采用的读取接口与局限。

军事控制分开记录 `PLAYER`、`BACKGROUND` 和 `ENGINE` 来源：

- 后台军事命令和后台征取请求必须为零；玩家确认征取可以产生对应的一次军事动作，不能混入后台计数。
- 回合刷新会恢复行动力，敌方会造成伤害，玩家原有多回合路线会继续行军。不能要求整个二十回合军队坐标和行动力绝对不变。
- 在受控动作窗口比较前后状态与请求来源；对护送编队专门检验自动文职移动没有带动护卫，且没有偷偷解除编队。
- 仅观察“军队没动”不足以证明没有命令，须结合操作入口审查、来源记录和实际状态；记录不完整则不能断言隔离通过。

费用用恒等式核验：`后余额 = 前余额 + 窗口内正常收支 - 本次实际结算 + 本次合法补偿`。行动、资源、人口与次数按类似方法计算。缩短窗口并尽量停留同回合，避免将回合收入误认成退款。

结果未知时，要把“已发送”“观察到所有者变化”“已证实由该请求成功并结算”分开。超时不是失败，所有者变成白绮也不单独证明是这次请求造成；不能据此重发或退款。对账恢复要有请求关联和原执行记录等实现可提供的证据；证据不足则保持冻结并报告阻塞。

完整请求、机器日志、截图与私人存档存于被忽略的 `.local-model/<run_id>/` 或该机器外置数据目录。公开 `docs/` 只存脱敏环境、结果摘要和可分享的证据索引，不提交游戏文件、账号信息或私人存档。公开结果中本机路径不能被当作其他机器可访问的附件。

## 运行顺序与回归

1. 冻结配置、建立夹具与对照，先验证夹具确实满足前置条件；夹具缺失记 `BLOCKED`。
2. 跑身份／所有者隔离、手动接管和军队隔离，再跑生产、区域、建造者与正常扩张。隔离失败时停止相关自动执行，修复后回归受影响用例。
3. 征取先测资格／报价／取消，再测真实城市转移、资产变化、单独资产控制，最后跑重复、明确失败、未知与恢复分支。使用独立存档副本，不靠上一例偶然残留状态。
4. 基础行为达到要求后跑五城二十回合、十城性能及经济压力，最后核对版本和声明的兼容范围。
5. 每次代码修改按受影响需求重跑；控制权、转移、支付和恢复共享路径改变时，补相关关键回归。纯文档修改只校验文档，不将无关游戏测试伪装为必要验证。

## 判定与退出标准

| 状态 | 使用条件 |
| --- | --- |
| NOT_RUN | 尚未尝试，当前所有游戏用例均为此状态。 |
| PASS | 前置成立，步骤完成，所有预期均有足够引擎证据；标明仅静态／逻辑通过时，不能算游戏 PASS。 |
| FAIL | 运行得到明确不符合预期的结果；登记缺陷与关联需求。 |
| BLOCKED | 未实现、缺夹具／参数／能力或无法取得必要证据；不得算通过。 |
| NOT_APPLICABLE | 仅用于明确不在该版本支持矩阵的可选类别，说明依据；核心三项自动化、军队指挥权、城市与独立建筑夺取目标不得借此豁免。 |

抢走军队控制、错误夺取他人资产、重复收费／获利、未授权扣费、存档损坏属于阻断交付缺陷。普通功能不满足其需求同样不能记该项通过；性能超过冻结预算记失败，原因不清记阻塞。

完整验收要求 BR-001～BR-028 均有对应通过证据、支持矩阵内必需用例全部通过、无未解决阻断缺陷。单独区域／改良类别可以按冻结的支持矩阵报告范围，但 BR-019 的独立建筑与其他设施目标必须保留；没有可行机制就明确尚未达到完整需求。部分里程碑只能用“生产部分通过”等名称交付。
