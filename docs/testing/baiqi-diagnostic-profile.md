# 外部计时工具的语义验证

tools/lua/diagnostic_profile.lua 是开发者外部诊断模块，不进入可安装模组；首次验证时游戏代码为47版。它返回 NewProfile(clock, capacity)，由负责人在独立诊断中选择包装对象，没有玩家入口或托管开关。

state:Wrap(name, fn) 返回包装函数：原函数只调用一次，参数、所有返回值和错误对象保持原样，包括 false、中间及尾部 nil。调用计数持续增加，样本容量固定；时钟异常、非数、非有限值、倒退或差值溢出只记无效区间，不制造零耗时，也不阻断原函数。invalidClock 按调用区间计数，dropped 只记录超过容量的有效样本。

样本是函数的**包含嵌套调用耗时**。不能把嵌套样本相加当作模组总耗时。该工具没有自动注册回调、代理游戏管理器、恢复现场、划分回合、记录游戏动作或建立对照的功能；这些由具体诊断脚本另行完成。

2026-11-02验证：

- 10项针对性软件测试通过，覆盖任意长度参数／返回值、零返回值、false 入参、错误对象、异常／缺失／倒退时钟、容量与嵌套语义。
- 同样消费者加载本地模型182候选，仅增加导出其工厂的适配尾句、不修改函数体，10项均产生断言错误；该候选没有进入游戏。
- Civ6当前47版、11城90回合的UI Lua中，负责人模块通过纯虚拟函数与虚拟时钟的兼容检查：保持4个返回值及尾部 nil、错误对象和时钟失败行为。没有包装实际游戏函数或测量游戏性能。
- 原生确认 Automation.GetTime 为函数，ContextPtr.GetUpdate、debug、table.pack、table.unpack 不可用；使用已有的全局 unpack。当前计时分辨率尚未重新测量。

软件命令：

    python -m unittest discover -s tests -p test_diagnostic_profile.py -v

源码指纹、实际原生标记与采用边界见[工具证据](../research/baiqi-p6-profile-tool-evidence-2026-11-02.json)。

TC-036仍未通过。下一步须冻结预算／样本窗口，补齐模块覆盖及去重计时，建立匹配的十城行为关闭对照；当前11城终态和早前32／34版的Controller单独计时不能替代这些条件。历史包装会丢失 allowOrders 参数，不能直接复用到47版。

## 2026-11-03：资格查询分项

[diagnostic_qualification.lua](../../tools/lua/diagnostic_qualification.lua) 复用上述工厂，在负责人创建的计数代理上一次性包装 CanStartOperation／CanStartCommand。仅在实际规划观测记录存在时计时；其他调用直接透传。它不安装全局代理、不注册回调、不发送游戏操作，也不进入69文件的玩家版模组。

每条规划记录分别保留查询包含耗时、有效样本数和未知区间数，状态的 qualProfile 提供无效时钟及容量丢弃统计。原函数参数、零／多返回值、中间和尾部nil及错误身份保持，原生异常不重试。时钟失败仍执行查询，记录未知；这些分项可能嵌套，不能与规划包含时间相加当作总开销。额外诊断计时本身的原生开销尚未校准，不能与旧观测器的数值换算成因果提速。

10项新模块测试与10项既有工厂测试通过；本地模型203的原始绑定遗漏报告所用的qualProfile，原9项消费者测试出现1FAIL／1ERROR。负责人补接统计状态、使模块自行提供pack后，同一9项报告消费者通过。软件通过尚不代表原生54性能通过。[采用与验证证据](../research/baiqi-p6-qualification-tool-evidence-2026-11-03.json)。

## 2026-11-03：保存实际区间端点

工厂存储的有效样本增加started／ended，直接保留原有两次时钟读取的值，未增加时钟调用。20项已有工厂／资格绑定检查通过；另以真实工厂消费者核实起止1／2、差值1，时钟只读2次、被测函数只调用1次。

该小改动按负责人明确字段合同原样采用本地模型207的单一片段，为后续区间去重提供数据。正在运行的55版q7观察器仍使用冻结的旧工厂，不能把新字段追认到已有样本；全模块收集、跨上下文时钟校准和去重累计尚未完成。[采用范围](../research/baiqi-p6-profile-interval-source207-evidence-2026-11-03.json)。

## 2026-11-03：区间去重与55时钟初查

[纯工具](../../tools/profile_intervals.py)用于已校准同一时钟域的区间合并，避免嵌套重复相加；尚无全模块采集器，不能判B_turn通过。模型209合并算法部分采用，形状校验与溢出处理由负责人修正；原候选12测试有6处失败、1错误，修正后12项通过，含3375组独立整数格覆盖对照。208截断整弃且未读；210分析有局部函数／Native调用及UnitSnapshot归属错误，拒绝。55实机只读连续4096次时钟读取有7次正增量、4089次零、0次负增量，最小观测约1ms；os.clock实际存在，但尚未校准CPU关系、观测开销或跨上下文关系。[证据](../research/baiqi-p6-interval-union-source209-evidence-2026-11-03.json)。

## 2026-11-03：双计时兼容与CPU计时不可用证据

模型211把包装组合写成先调用后把结果再传给原函数，且不符合冒号调用合同，原8项7错误；候选未接入游戏。负责人重写[薄包装](../../tools/lua/diagnostic_dual_profile.lua)，8项通过，原生纯函数参数／返回值与只调用一次也通过，模型源码采用0。原生三组各1000次空函数调用：直接约1–2ms、单计时约36–41ms、双计时约79–86ms；这只是纯循环观测，不能扣除实际游戏回调时间。os.clock的所有增量均为0，CPU关系未知，不能宣称CPU工作为0或确定调度暂停。下一轮只用轻量墙钟，不安装查询／动作代理；当前55性能仍FAIL。[分层证据](../research/baiqi-p6-dual-profile-source211-evidence-2026-11-03.json)。
